# 执行与验收：AI Coding、按模块验收、整体验收

进入 accept 模式时读这份。

## 1. 执行纪律

- **先读后改**：动手前通读相关代码与对应文档，理解现有约定再改。
- **一次一个模块**：不把多个模块塞进一次改动，否则出问题无法归因。
- **只改必须改的**：每行改动都要能追溯到本次需求；不顺手重构无关代码、不改格式、不动无关文件。
- **不做需求外的功能、抽象、配置**。
- **新技术栈先问**：要引入未被声明的框架、库、外部服务时，先问用户再引入。
- **用原生写文件工具**编辑文件。不要用 shell here-string / 字符串拼接生成多行文件内容，
  容易出现字面转义符并把标题、锚点写坏；改动后 `grep` 一下标题与关键锚点确认完好。
- **静态检查自己跑**：类型检查、lint 必须自己跑通过再交付，不要留给用户发现。
- **失败先复现**：报 bug 时先写一个能稳定复现的最小场景，再改。

### 改完自检（按改动类型选做）

- 改动涉及 UI：用真实浏览器打开，走一遍主路径；每个断点至少看一次；控制台无报错。
- 改动涉及接口：先直接请求接口确认返回体形态，再看前端。
- 改动涉及数据：确认所有语言的 mock 文件 id 集合一致、字段名一致。
- 改动涉及行为：同步回写对应文档（见 SKILL.md 变更回写表）。
- 改动涉及文案：多语言字典同时补齐，检查是否残留旧键或旧文案。

## 2. 按模块验收

**每完成一个模块/功能，先让用户验收，通过后再进入下一个。** 不要一口气做完再交付。

交付说明包含四件事：

1. **改了什么**：文件路径 + 一句话说明。
2. **怎么验**：用户能直接执行的步骤或入口（页面路径、命令、账号）。
3. **证据**：可复核的量化证据——命令输出、测量数值、截图、帧率/耗时等。
   不要只说「已优化」「很流畅」「应该没问题」。
4. **已知限制**：没做到的、有取舍的、需要用户决策的，明确写出来。

验收不通过时：先复现用户描述的现象，定位根因再改，不要凭猜测打补丁。

## 3. 最终整体验收

全部模块做完后，做一次以文档为基准的整体核对：

- **逐条对照**：prd.md 的每个功能、page-specs.md 的每页、ui-patterns.md 的每条规范，
  都能在代码里找到对应实现；对不上的要么改代码，要么改文档（并说明为什么）。
- **关键路径走查**：未登录 → 登录 → 核心操作 → 失败分支 → 退出，全流程走一遍。
- **全局一致性**：术语、文案、颜色、间距、组件用法、错误提示位置。
- **站点结构**：按 prd.md §7 的层级树核对——每页都在树里、入口列非空；
  头部项数、页脚分组、面包屑符合 ui-patterns.md §8，URL 与导航层级一致（命名约定见 ui-patterns.md §9）。
- **响应式与可访问性**：全部断点、键盘可达、焦点可见、对比度达标。
- **文档与代码同步**：六份文档反映的是当前实现，不是某个早期版本。
- **跨文档去重**：同一数值、术语、Route 若在两份文档各写一遍即违规——只留一处，其余改成引用。

输出格式：

```text
通过项：…
不通过项：…（含复现步骤与影响）
已知取舍：…（为什么这样选）
```

## 4. 成品自检底线（UI）

改完 UI 后逐条核对**已建好的结果**，不是意图。都在同一轮渲染里看，不要为每条单独跑一遍。

- **对比度**：正文与占位文字 ≥ 4.5:1，大字 ≥ 3:1。彩色底上的次级文字从该色相调暗或调亮，**不要用灰**。
- **层次**：阴影要有偏移 + 柔和模糊；零偏移的彩色光晕是装饰，不是层次。
- **间距**：相关元素靠紧、不同组拉开；标题上方的留白多于下方。读实际计算值，不靠目测。
- **字体**：正文行宽 65–75 字符，display 不超过 6rem，字距不小于 -0.04em；标题用平衡换行；用真实文案在每个断点跑一遍，修掉溢出。
- **动效**：一个有意为之的时刻，而不是散落各处、或每个区块同一个入场。ease-out 入场，只动 `transform` / `opacity`；clip-path、mask、shadow 只要不掉帧也可用（`blur` 系列见下条的性能约束）。
- **性能**：`backdrop-blur` 只用在 fixed / sticky 元素，绝不用于滚动容器或大内容区（持续重绘、移动端掉帧）；噪点 / 颗粒纹理只挂 fixed 且 `pointer-events-none` 的伪元素；滚动动效不用 `window.addEventListener('scroll')`，改用 `IntersectionObserver` / `whileInView`。
- **全屏与回落**：全屏高度用 `min-h-[100dvh]`，不用 `h-screen`（防 iOS Safari 地址栏跳动）；非对称或重叠布局在 <768px 回落为单列 + `w-full`，重叠一律拆开（避免触摸目标冲突）。
- **状态**：hover、disabled、loading、error、empty 五态齐全，加上真实内容、可用控件、键盘焦点（具体呈现见 page-specs.md / ui-patterns.md）。
- **浏览器原生表面**：文字选择色、caret、滚动条、焦点环、下划线偏移、表格数字，这些默认值不属于任何设计系统，必须按调色板主题化。这是「页面被做出来、而不是拼出来」最便宜的信号，也最容易被跳过。
- **文案**：按 ui-patterns.md §11 的文案规范核对（命名、控件动作、错误、空态、语气）。
- **覆盖度**：brief 的每条要求都在，且几秒内能找到。

## 5. 修复优先级

审计与走查出的问题，按下面的顺序修，不要按「哪个好修」或「哪个显眼」排序：

1. 坏掉或卡住的任务、数据丢失、误导状态、不可达路径；
2. 缺失的加载 / 空 / 错误 / 成功 / 禁用 / 权限状态；
3. 流程、层级、响应式、设计系统漂移；
4. 视觉与动效不一致；
5. 代码与资产清理。

不要在某个角落做到完美，却让其余部分低于同一条质量线。

## 6. 有界验证

验证是**有界**的，不是循环：

- 一次把该看的看完——桌面与移动同批看，不要为每条检查单独跑一遍。
- 一轮把该修的全修完。
- 之后最多再确认一轮，就停。

开放式自我 QA 会花掉用户的钱，去做完成度交接能做得更好的事。宁可把剩余问题如实报出，也不要无限打磨。

## 7. 停止条件

- 用户验收通过并明确说「继续下一个」，才进入下一个模块。
- 用户没要求时，不要一次改多个模块，也不要顺手做「顺便优化」。
- 发现需求外的缺陷：报告它，不要默默修（除非用户同意）。
